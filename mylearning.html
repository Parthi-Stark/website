Cyber Security Learning My Journey

Author: Parthiban S

Web traffic flow Browser ↓ DNS ↓ IP address ↓ TCP connection ↓ TLS handshake ↓ HTTP request ↓ Network routing ↓ Firewall ↓ Load Balancer ↓ WAF ↓ Web Server ↓ Application ↓ Database ↓ Application ↓ Web Server ↓ WAF ↓ Load Balancer ↓ Firewall ↓ Internet ↓ Browser Browser: Laptop Mobile Browser Mobile application API client Another server For example: Windows 11 ↓ Chrome ↓ https://example.com Operating system Examples: Windows Linux macOS Android iOS The OS manages: Network interfaces TCP/IP stack Processes Memory Files Ports Routing table DNS configuration Certificates Encryption libraries 4. Application/browser creates the request You enter: https://example.com/login The browser understands: Protocol = HTTPS Hostname = example.com Port = 443 Path = /login HTTPS is essentially: HTTP + TLS encryption Normally: HTTP → port 80 HTTPS → port 443 5. DNS happens first The browser needs to know: What IP address belongs to example.com? It asks DNS. For example:example.com ↓ 203.0.113.10 The actual DNS chain can involve: Browser DNS cache ↓ OS DNS cache ↓ Configured DNS resolver ↓ Root DNS ↓ .com DNS ↓ Authoritative DNS ↓ IP address In enterprise environments you may see: Client ↓ Corporate DNS ↓ DNS security ↓ Recursive resolver ↓ Authoritative DNS 6. DNS records You should know these well as a security engineer. A record Maps hostname to IPv4. example.com → 203.0.113.10 AAAA IPv6. example.com → 2001:db8::1 CNAME Alias. www.example.com ↓ example.company.com MX Mail server. TXT Often used for: SPF Domain verification Security policies NS Name servers. 7. CDN / DDoS protection Large applications often have: User ↓ CDN ↓ Origin Examples include: Cloudflare Akamai AWS CloudFront Azure Front Door The CDN can provide: Caching DDoS protection TLS termination Bot protection Rate limiting Geographic distribution For example: User in India ↓ Indian CDN edge ↓ Origin in Singapore The user doesn't necessarily connect directly to the origin server. P networking starts Now suppose DNS returned: 203.0.113.10 The client needs to communicate with that IP. This involves the TCP/IP networking stack. You should understand: Application ↓ Transport ↓ Internet ↓ Network Access Or commonly: HTTP TLS TCP IP Ethernet/Wi-Fi 9. TCP connection For HTTPS, TCP normally uses: Destination port = 443 TCP establishes a connection using the famous: SYN ↓ SYN-ACK ↓ ACK This is the TCP three-way handshake. Example: Client Server SYN ------------------------> <---------------- SYN-ACK ACK ------------------------> Now TCP connection is established. 10. What does TCP actually do? TCP provides: Reliable delivery Sequencing Retransmission Flow control Congestion control Imagine the HTTP data is large. TCP breaks it into segments. HTTP data ↓ TCP segment 1 TCP segment 2 TCP segment 3 TCP segment 4 The receiver reassembles them. 11. IP layer TCP sits above IP. IP decides: Where should this packet go? Example: Client IP: 192.168.1.20 Destination: 203.0.113.10 The packet travels through multiple routers. Laptop ↓ Home/Corporate router ↓ ISP ↓ Internet routers ↓ Cloud/provider network ↓ Data center Routers examine the destination IP and forward packets. 12. MAC addresses At the local network level you also have: IP address MAC address For example: IP: 192.168.1.20 MAC: AA:BB:CC:DD:EE:FF ARP can resolve: IP → MAC within an IPv4 local network. You don't normally have the client's MAC address travelling across the Internet. That's an important distinction. 13. Firewalls Now the request reaches your enterprise infrastructure. One of the first security controls could be a firewall. For example: Internet ↓ Firewall Examples: Palo Alto FortiGate Check Point Cisco Azure Firewall AWS Network Firewall A firewall can inspect: Source IP Destination IP Source port Destination port Protocol Application User URL Threat intelligence depending on its capabilities. 14. Firewall example Suppose: Source: 1.2.3.4 Destination: 203.0.113.10 Protocol: TCP Destination port: 443 Firewall rule: Internet → Web VIP TCP/443 ALLOW Everything else might be denied. For example: Internet → Web VIP TCP/22 DENY That's basic segmentation. 15. Stateful firewall A stateful firewall remembers connections. For example: Client → Server TCP 443 After allowing the connection, it knows that the return traffic belongs to the same session. Conceptually: Client:54321 → Server:443 Response: Server:443 → Client:54321 The firewall understands this connection state. 16. Load Balancer Suppose your application has: Web Server 1 Web Server 2 Web Server 3 You don't want users to connect directly to individual servers. Instead: Load Balancer │ ┌─────────┼─────────┐ ↓ ↓ ↓ Web01 Web02 Web03 The user connects to a VIP. Example: www.example.com ↓ 203.0.113.10 ↓ Load Balancer VIP The load balancer chooses a backend. 17. Load-balancing algorithms Common algorithms: Round Robin Request 1 → Server 1 Request 2 → Server 2 Request 3 → Server 3 Request 4 → Server 1 Least Connections Send the request to the server with fewer active connections. Weighted Server 1 → 50% Server 2 → 30% Server 3 → 20% 18. Health checks The load balancer continuously checks backend servers. For example: GET /health Expected: HTTP/1.1 200 OK If: Server 2 → 500 the load balancer can mark it down. Then: Request → Server 1 Request → Server 3 instead. 19. Where does WAF come in? This is especially important for your job. There are several architectures. Architecture A Internet ↓ Firewall ↓ WAF ↓ Load Balancer ↓ Web Server Architecture B Internet ↓ Firewall ↓ Load Balancer ↓ WAF ↓ Web Server Architecture C WAF functionality may be integrated into an ADC/load balancer. For example: Internet ↓ F5 ├── Load Balancing └── ASM/Advanced WAF ↓ Web Servers The exact placement depends on the architecture. 20. What does the WAF actually inspect? Suppose the browser sends: GET /products?id=123 HTTP/1.1 Host: example.com Cookie: session=abc123 User-Agent: Chrome The WAF can inspect: Request method GET POST PUT DELETE PATCH URL /products?id=123 Headers Host Cookie User-Agent Content-Type Authorization Query parameters ?id=123 POST body For example: { "username": "parthiban", "password": "xxxxx" } 21. WAF security checks Typical WAF protections include: SQL Injection ' OR 1=1 -- XSS Path traversal ../../etc/passwd Command injection ; cat /etc/passwd Protocol violations Malformed HTTP requests. HTTP method restrictions Example: GET → allowed POST → allowed DELETE → blocked Rate limiting For example: 1000 requests/minute/IP Bot protection Detecting automated traffic. 22. WAF does NOT replace a firewall This is a very important concept. A network firewall primarily controls network traffic. For example: IP Port Protocol Network Zone A WAF primarily protects web applications. For example: HTTP URL Parameters Headers Cookies Request body Application attacks So: Firewall: "Can this network connection reach the service?" WAF: "Is this HTTP request acceptable for this application?" 23. TLS / SSL Before the HTTP data can be securely exchanged, TLS is involved. Modern HTTPS generally uses: TLS 1.2 TLS 1.3 The TLS handshake establishes: Server authentication Encryption keys Secure communication The server presents a certificate. Example: Certificate: CN = example.com Issuer = Trusted CA The browser verifies the certificate chain. 24. TLS termination In many enterprise architectures: Client │ HTTPS ↓ WAF / Load Balancer │ HTTP or HTTPS ↓ Backend TLS terminates at the WAF/LB. Alternatively: Client ↓ HTTPS WAF ↓ HTTPS Load Balancer ↓ HTTPS Web Server This is called TLS re-encryption / SSL bridging depending on architecture. 25. Why does the WAF need TLS termination? Because encrypted traffic looks like: Random encrypted bytes The WAF cannot inspect: SQL injection XSS URL POST body unless it can decrypt the traffic. So: HTTPS ↓ TLS termination ↓ HTTP inspection ↓ WAF rules This is a major WAF concept. 26. HTTP request reaches the web server Assume the WAF allows: GET /login The request reaches: NGINX or: Apache or: IIS The web server receives the HTTP request. 27. Web server vs application server This distinction is extremely important. Web server Examples: NGINX Apache IIS Common responsibilities: Receive HTTP TLS termination Serve static files Reverse proxy Compression Headers Routing Access logs Application server Examples: Tomcat .NET Node.js Gunicorn uWSGI The application server executes application code. 28. Example architecture Suppose you have a Java application. Internet ↓ Firewall ↓ WAF ↓ Load Balancer ↓ NGINX ↓ Tomcat ↓ Java Application ↓ Oracle DB The request might travel: GET /login ↓ NGINX ↓ Tomcat ↓ Java code ↓ Oracle 29. Programming language enters here Your application could be written in: Java Java + Spring Boot C# ASP.NET Core JavaScript Node.js Python Django Flask FastAPI PHP Laravel WordPress The WAF generally doesn't care what language is used. It protects the HTTP interface exposed by that application. 30. What happens inside the application? Suppose you request: GET /user/123 The application might execute: HTTP Request ↓ Router ↓ Controller ↓ Authentication ↓ Authorization ↓ Business Logic ↓ Database Query For example: GET /user/123 might invoke: UserController ↓ UserService ↓ UserRepository ↓ Database 31. Authentication The application may determine: Who is this user? Examples: Username/password OAuth OIDC SAML JWT Session cookie MFA For example: Authorization: Bearer eyJhbGci... The application validates the token. 32. Authorization Authentication answers: Who are you? Authorization answers: What are you allowed to do? Example: User → Read profile Admin → Read + modify users This is application-level security. 33. Database The application may need information from: MySQL PostgreSQL Oracle SQL Server MongoDB Redis Example: Application ↓ SELECT username,email FROM users WHERE id=123 ↓ Database The database returns: username = Parthiban email = ... The application processes it. 34. Database should NOT normally be Internet-facing Good architecture: Internet ↓ WAF ↓ Web/App ↓ Database Bad architecture: Internet ↓ Database Database networks are usually protected by: Firewall Security groups Network ACLs Private subnets Authentication Encryption Least privilege 35. Internal networking Inside a data center/cloud, you might have: DMZ ↓ Web subnet ↓ Application subnet ↓ Database subnet Example: Internet ↓ DMZ ↓ Web Tier ↓ App Tier ↓ DB Tier This is network segmentation. 36. Linux server A huge percentage of web infrastructure runs Linux. You should understand: Linux ├── Kernel ├── Processes ├── Memory ├── Filesystem ├── Network stack ├── Users/groups ├── Services └── Security For example: Ubuntu RHEL Rocky Linux Amazon Linux Debian 37. Linux process Suppose NGINX is running. You might see: nginx as a process. Application: java Database: mysqld Each application is a process. 38. Linux ports Example: NGINX → 443 Tomcat → 8080 SSH → 22 MySQL → 3306 You might have: WAF ↓ TCP/443 ↓ NGINX ↓ TCP/8080 ↓ Tomcat The application doesn't necessarily listen directly on 443. 39. Reverse proxy NGINX might act as a reverse proxy: Client ↓ NGINX :443 ↓ Tomcat :8080 NGINX receives: https://example.com and forwards internally: http://10.10.20.15:8080 40. Containers Modern applications often don't run directly on a physical/VM server. You might have: Server ↓ Docker ↓ Container ↓ Application For example: Kubernetes ├── Pod │ └── Java application ├── Pod │ └── Java application └── Pod └── Java application The request might therefore go: Internet ↓ WAF ↓ Load Balancer ↓ Kubernetes Ingress ↓ Service ↓ Pod ↓ Application This is increasingly important for WAF engineers. 41. Kubernetes networking A simplified architecture: Internet ↓ WAF ↓ Load Balancer ↓ Ingress ↓ Service ↓ ┌─────┴─────┐ ↓ ↓ Pod 1 Pod 2 The service distributes traffic to pods. 42. Microservices Modern applications may not be one application. Instead: Frontend ↓ API Gateway ↓ ┌───────────┬────────────┬────────────┐ ↓ ↓ ↓ ↓ User Payment Order Product Service Service Service Service ↓ ↓ ↓ DB DB DB Your original request may therefore trigger dozens of internal requests. 43. API Gateway An API gateway can provide: Authentication Routing Rate limiting API management Logging Transformation Authorization Architecture: Internet ↓ WAF ↓ API Gateway ↓ Microservices 44. The response Suppose the application generates: HTTP/1.1 200 OK Content-Type: application/json { "username": "Parthiban" } The response travels backward: Application ↓ Web Server ↓ WAF ↓ Load Balancer ↓ Firewall ↓ Internet ↓ Client 45. WAF also inspects responses Depending on configuration/product, WAF/security controls can inspect response traffic too. For example: Request inspection ↓ Application ↓ Response inspection Response controls can involve: Data leakage detection Sensitive information protection Response headers Cookie security Information disclosure 46. HTTP response headers You should become very comfortable with these. For example: HTTP/1.1 200 OK Content-Type: text/html Content-Length: 4521 Set-Cookie: session=abc Strict-Transport-Security: max-age=31536000 Content-Security-Policy: ... X-Content-Type-Options: nosniff Security headers are an important part of web security. 47. Cookies The server might return: Set-Cookie: session=ABC123 The browser stores it. Then subsequent requests contain: Cookie: session=ABC123 Cookie security attributes include: Secure HttpOnly SameSite Domain Path Expires/Max-Age For example: Secure means the cookie should be sent over HTTPS. HttpOnly prevents normal JavaScript access to the cookie. 48. Sessions A common architecture: Browser ↓ Session Cookie ↓ WAF/LB ↓ Application ↓ Session store Session storage might use: Redis Database Application memory If multiple application servers exist, centralized session storage or other session strategies may be needed. 49. Source IP becomes important to WAF Suppose: Client ↓ CDN ↓ WAF ↓ LB ↓ Server The backend server may see: WAF IP instead of the actual client IP. The original IP may be forwarded in headers such as: X-Forwarded-For or a provider-specific header. This is extremely important for: WAF policies Rate limiting Logging IP blocking Incident response But blindly trusting client-supplied forwarding headers can create security problems. 50. NAT Another concept you need to understand. Suppose internal server: 10.10.10.20 is behind NAT. External traffic may see: 203.0.113.20 NAT translates addresses. Private IP 10.10.10.20 ↓ NAT ↓ Public IP 203.0.113.20 51. SNAT and DNAT SNAT Source NAT. 10.10.10.20 ↓ 203.0.113.20 DNAT Destination NAT. For example: Public VIP 203.0.113.10:443 ↓ 10.10.20.10:443 Load balancers/firewalls commonly perform forms of NAT. 52. Routing Every network device needs to determine: Where should I send this packet? Example routing table: Destination Gateway 10.10.0.0/16 internal 0.0.0.0/0 firewall The default route: 0.0.0.0/0 means: If no more specific route exists, send it here. 53. VLANs Enterprise networks often separate traffic using VLANs. For example: VLAN 10 → Management VLAN 20 → Web VLAN 30 → Application VLAN 40 → Database This provides logical network separation. 54. Security groups / cloud networking In AWS/Azure/GCP you may additionally have: VPC/VNet ↓ Subnet ↓ Security Group / NSG ↓ VM For example: Internet ↓ Azure Application Gateway/WAF ↓ NSG ↓ VM Cloud networking adds another layer to understand. 55. Authentication infrastructure Enterprise applications often integrate with: Active Directory LDAP Azure AD / Entra ID Okta Ping Identity Keycloak A login request could therefore travel: Browser ↓ WAF ↓ Application ↓ Identity Provider ↓ Active Directory 56. Certificates and PKI You should understand: Private key Public key Certificate CA Certificate chain CSR OCSP CRL For example: example.com certificate ↓ Intermediate CA ↓ Root CA This is critical for WAF/ADC work because you'll frequently deal with certificate installation and TLS troubleshooting. 57. Logging Every layer generates logs. Firewall src=1.2.3.4 dst=10.10.10.10 port=443 action=allow WAF client=1.2.3.4 url=/login attack=SQL Injection action=blocked Load Balancer VIP=10.10.10.10 pool_member=10.20.20.5 status=200 NGINX GET /login 200 Application User login successful Database May record queries, errors, authentication events, etc. 58. SIEM All these logs can eventually flow into: Firewall ↓ WAF ↓ Server ↓ Application ↓ SIEM Examples: Splunk Microsoft Sentinel QRadar Elastic The SOC can correlate events. For example: 1000 requests ↓ Same IP ↓ WAF SQLi blocks ↓ Firewall events ↓ SIEM correlation ↓ SOC alert 59. Monitoring Separate from security logs, infrastructure monitoring watches health. Examples: CPU Memory Disk Network Latency Connections Errors Throughput Tools include: Prometheus Grafana Datadog New Relic Dynatrace Zabbix 60. What happens when something fails? This is where your understanding becomes really valuable as a WAF engineer. Suppose: User says: "Website is down." Don't immediately assume WAF. Trace the path: DNS ↓ Internet ↓ Firewall ↓ VIP ↓ WAF ↓ Load Balancer ↓ Pool ↓ Web Server ↓ Application ↓ Database At every stage ask: Is the request reaching this layer? 61. Example troubleshooting User receives: Connection timed out Possible causes: DNS issue Routing issue Firewall drop Security group Load balancer WAF Backend unavailable But if they receive: HTTP 403 then the request probably reached an HTTP-aware component. Potentially: WAF Application Authentication layer 62. 403 vs 404 vs 500 vs 502 vs 503 Know these extremely well. 200 Success 301/302 Redirect 400 Bad request 401 Authentication required/failed 403 Forbidden Could be WAF or application. 404 Resource not found 429 Too many requests 500 Application/server error 502 Bad gateway Often proxy/LB cannot get a valid backend response. 503 Service unavailable Backend/pool/service may be unavailable. 504 Gateway timeout Proxy/LB waited too long for upstream. 63. WAF troubleshooting example Suppose customer says: POST request is getting blocked. You should investigate: Client IP ↓ URL ↓ HTTP method ↓ Host ↓ Headers ↓ Parameters ↓ Request body ↓ WAF policy ↓ Signature/rule ↓ Action For example: POST /login username=admin password=' OR 1=1 -- WAF may detect: SQL Injection and return: 403 64. But what if WAF allows it? Then trace: WAF → LB Check: Pool Health monitor Routing SNAT Backend connection Then: LB → Web Server Then: Web Server → Application Then: Application → Database This is why understanding the entire stack makes you much stronger at WAF troubleshooting. 65. OSI model you should know For your career, memorize this conceptually. Layer 7 → Application HTTP, HTTPS, DNS Layer 6 → Presentation TLS, encoding Layer 5 → Session Layer 4 → Transport TCP, UDP Layer 3 → Network IP, routing Layer 2 → Data Link Ethernet, MAC, VLAN Layer 1 → Physical Cable, fiber, radio WAF primarily operates around: Layer 7 Firewalls can operate across multiple layers depending on capability. 66. TCP/IP model In practical troubleshooting, you'll often use: Application ↓ Transport ↓ Internet ↓ Network Access For web security: HTTP ↓ TLS ↓ TCP ↓ IP ↓ Ethernet That's a very useful mental model. 67. The entire journey in one example Let's put everything together. User enters: https://bank.example.com/login Step 1 Browser checks its DNS cache. Step 2 DNS resolves: bank.example.com → 203.0.113.50 Step 3 Client establishes TCP: Client → SYN Server → SYN-ACK Client → ACK Step 4 TLS handshake occurs. Step 5 Browser verifies the certificate. Step 6 Browser sends: POST /login HTTP/1.1 Host: bank.example.com Content-Type: application/json {"username":"user","password":"xxxxx"} Step 7 Internet routers forward packets. Yes. In fact, hands-on is the best way for you to learn this, especially because you're already working in WAF. You can build a small enterprise-style lab on your Windows 11 laptop and reproduce almost the entire request path yourself. I’d recommend building it progressively rather than trying to install everything at once. Your lab will eventually look like this YOUR LAPTOP │ ┌────────┴────────┐ │ │ Windows 11 Linux VMs │ │ │ ┌──────┴──────────┐ │ │ │ Browser Firewall Web/App │ pfSense/OPNsense Server │ │ │ └──────────┼─────────────────┤ │ NGINX │ WAF simulation │ Web Application │ Database Then you can progressively add: DNS ↓ Firewall ↓ Reverse Proxy / Load Balancer ↓ WAF ↓ NGINX ↓ Application ↓ Database ↓ SIEM / Monitoring
